# BSFM Research Observatory — web architecture

Date: 2026-09-06
Status: complete public-page architecture

## Purpose

The public web surface is part of the scientific audit trail, not a marketing dashboard. It must make uncertainty, blocked gates and negative evidence at least as visible as a prospective forecast.

## Pages

- `site/index.html` — research overview, current gate state, acquired data and routes to the complete audit surfaces.
- `site/forecast.html` — dedicated F-002 dossier generated from the frozen record, including scoring boundaries, descriptive geography, unsupported operator/MSN and automatically refreshed comparables.
- `site/validation.html` — global G1–G4 state and the separate BSFM-PD 1.3 out-of-sample result, including the negative candidate-vs-baseline score and frozen event-fold threshold.
- `site/methodology.html` — immutable forecast→outcome→score protocol, automatic refit/time-distribution cycle, uncertainty, model lineage and version-change rules.
- `site/provenance.html` — source inventory, PIT semantics, machine-readable artifacts, evidence roles and licensing/privacy boundaries.
- `site/styles.css` — shared responsive observatory design system.
- `site/page-copy.js` — bilingual copy for the expanded page surfaces.

## Generated public state

`AGGIORNA` writes and commits:

- `site/data/status.json` — source/registry/run state generated by the pipeline;
- `site/data/forecast.json` — exact public projection of canonical frozen F-002 fields;
- `site/data/final-readiness.json` — machine-readable scientific readiness derived from the foundation and lifecycle audits;
- `site/data/research-state.json` — annual G1 detail plus fail-closed G2/G3/G4 and resolution state used by the validation page;
- `site/data/public-data-validation.json` — all BSFM-PD 1.3 exploratory backtest folds and summary scores;
- `site/data/research-cycle.json` — versioned automatic-cycle outcome and content hashes;
- `site/data/refinements.json` — append-only prospective refinement surface;
- `site/data/comparable-cases.json` — automatically selected nonfatal descriptive comparables.

The web pages read these JSON files with `cache: no-store`. They do not recompute scientific gates in JavaScript. Presentation reflects the Python audit result.

## Automatic publication

There remains exactly one workflow: `AGGIORNA`.

In the same integrated run it:
1. executes pre-refresh tests and integrity checks;
2. refreshes official source manifests and NTSB normalization;
3. executes post-refresh tests and scientific audits;
4. writes readiness, F-002 public projection, research state and cycle artifacts;
5. commits changed generated research state;
6. configures/enables GitHub Pages;
7. uploads `site/` as the Pages artifact;
8. deploys it to the `github-pages` environment.

No second Pages workflow is introduced. Therefore one successful AGGIORNA updates both the auditable repository state and the public observatory.

## Publication safety invariants

- Software PASS is never rendered as scientific validation.
- `BLOCKED` remains visible for unknown empirical evidence.
- Absolute accident probabilities remain OFF until promotion readiness is real.
- F-002 is labelled experimental and immutable.
- The site explicitly states that BSFM is not an operational safety tool and does not assess individual flights, aircraft, airlines, routes or people.
- Global traffic context is not rendered as Boeing-family exposure.
- Later refinements remain separate from the original F-002 score.
- Descriptive similarities, geography, operator and MSN cannot be rendered as successful forecast dimensions when unsupported.
- The negative/underpowered BSFM-PD 1.3 result remains visible and cannot be used to redesign version 1.3 retrospectively.

## Verification

`tests/test_site.py` protects the page inventory, bilingual/accessibility controls,
fail-closed copy, generated-state bindings, model-lineage boundary, single-workflow
rule and Pages deployment steps. `tests/test_public_forecast.py` prevents the
website projection from drifting from canonical F-002. The final AGGIORNA run is
the integrated runtime verification of this publication chain.
